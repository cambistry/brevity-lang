# `super`: the current function, one layer up — 2026-11-19

Decided in discussion. Gives `super` the meaning `base-and-super-2026-11-19.md` held it for,
Ruby style, and replaces that note's "Not adopted: `class::base()`" with `class::base`
(below). In `class-scope-and-inheritance-2026-11-16.md` it supersedes the merged params
(a subclass's `new` taking its parents' params) and "`super` in a class block is an error".

## The base is an actor; merged for now

- In concept, a subclass actor's parent layer is an actor of its own: the **base**. That
  matters for remote superclasses (`remote-superclass-2026-11-16.md`), where the base is
  built by an `$extend` and reached through facets. That mechanism waits.
- For now the base stays merged into the subclass actor, as today. The rules below are
  written so they still hold once the base is a separate actor.
- Late binding stays: the parent's code running for a `U` uses `U`'s overrides.

## In a constructor, `super` builds the base

```brevity
T = (n Integer) *{ … }
U = T ^ (label Text, n Integer) *{
  super(n * 2)            // T's constructor runs here, on the base
  …
}
V = T ^ (n Integer) *{ super }    // passes V's args as received: T's constructor gets n
```

- **No merged params.** A subclass's `new` takes its own params only, and passes what the
  parent needs through `super`, as is or amended.
- `super(args)` runs the parent's constructor on the base with `args`. Bare `super` passes
  the constructor's own args exactly as received, positional and named. `super()` passes none.
- The parent's constructor body runs at the `super` line, not before the subclass's body.
  A base name read before that line is an error.
- **Every path or none.** `super` is called exactly once on every path through the
  constructor, or on no path. An `if` whose branch calls it needs an `else` that calls it
  too. Never in a loop. A base that existed on only some paths would buy nothing: the
  subclass's code could use it only where it definitely exists.
- **No base.** A constructor that never calls `super` builds no base. The parent's state
  isn't allocated and its constructor doesn't run. This is legal only if the subclass
  defines the parent's whole public interface (its public functions and public cells, by
  name and arity), so the subclass is still substitutable for the parent. Protected names
  aren't required. It's for a subclass that would rather not carry the base's weight, and
  re-implements its behaviour instead.
- **Without a base,** a parent's name the subclass doesn't define is a compile error
  anywhere but assignment position: calls and reads both. That includes `super`, `base::`
  and `base.` in the subclass's functions. The parent's class block is still reachable
  (`class::base`, `T::x`).
- **Several parents:** `super[A](…)` and `super[B](…)`, each one on every path or none,
  each parent's interface rule applying when its `super` is never called. Bare `super` (with
  or without args) is an error when there is more than one parent.

## In a function, `super` calls the base's same function

```brevity
T = *{
  h = (n Integer) -> n + 1
  @a = (x Integer) -> x * 2
}
U = T ^ *{
  h = (n Integer) -> super * 10        // T's h with U's n: base::h(n)
  @a = (x Integer) -> super(x + 1)     // T's @a with x + 1: base.a(x + 1)
}
```

- `super(args)` in a function `h`, public or protected, calls the base's `h` with `args`:
  `base::h(args)` for a protected `h`, `base.h(args)` for a public `@h`.
- Bare `super` passes the current function's args exactly as received. `super()` passes
  none, so it isn't the same as `super` when the function has params.
- **One layer up is the parent's definition, not the next clause.** A `super` in a clause
  the subclass adds with `<<` or `>>` dispatches over the parent's clauses only. A `super`
  in a function no parent defines is an error.
- In a lambda inside `h`, `super` is `h`'s: lexical, as in a Ruby block.
- Several parents: `super[A](…)`. Bare `super`, or `super(…)`, is an error with more than
  one parent.
- No base (the constructor never called `super`): `super` in a function is a compile error.
- `super` is reserved. It can't be declared or set, and `super.x` and `super::x` stay
  ungrammatical: those are `base.x` and `base::x`.

## In a class block

```brevity
A = actor { @f = { init_count } }
B = A ^ { @f = { super + 1 } }
```

- A class block that extends another always has a base: the parent's block, which already
  exists (class blocks inherit by delegation). The constructor rules don't apply, and
  `super` in a class-block function is always valid. It runs the parent block's function for
  `B`, late-bound.

## `class::base`

- `class::base` is the running class's parent: Ruby's `self.class.superclass`. `class::`
  follows the running class, so in `T`'s code running for a `U`, `class::base` is `T`.
- `class::base::h` is the parent class block's protected `h`, `class::base.f` its public
  `@f`. `class::base(…)` constructs a separate actor of the parent class, as calling any
  class does. It isn't the base.
- With more than one parent, `class::base` is an error: write the parent's name.
  `class::base[A]` isn't supported, since it would just be `A`.
- No collision with a member: `base` can't be declared bare, so no protected member is
  named `base`. `class.base` is a public member `@base`, which differs only in `.` versus `::`.
