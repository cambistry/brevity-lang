# `use` — DI as its own declaration (2026-11-17)

Decided 2026-11-17. Replaces the `**` header as the way a file declares dependencies, and lifts its
head-of-file rule. Follows `file-singleton-header-2026-11-13.md` and
`di-destructure-orthogonality-2026-04-22.md`.

## Why DI is neither params nor a destructure

DI used to be modelled on constructor params, and the header syntax copied param syntax. That model
is wrong twice over:

- **A file isn't a constructor.** It's a singleton, an actor. Nobody calls it, so it has no params.
  All it can do is read names from outside itself.
- **The header is closer to a destructure** (`(HTML: (:div), :document) = context`), but the right
  side would always be the host. A token that never varies tells you nothing, and the left side
  doesn't follow destructure rules anyway (see the shorthand below).

DI is a separate thing: a request to the host. It gets its own keyword.

## Form

```brevity
use HTML, document
body

actor {
  Child = actor {
    use document
    …
  }
}
```

- `use` takes a list of header entries. The entry grammar carries over from the `**` header: paths,
  renames, types, nested destructures like `HTML: (:div)`.
- **Bare name shorthand:** `use HTML` means `use "HTML": HTML`, i.e. bind the host's `HTML` under
  the same name. Under destructure rules a bare `HTML` would be a syntax error, since it has no
  destination and no `:` sigil. That's fine, because `use` isn't a left-hand destructure. The shorthand
  makes it read like an import list, which is what it is.
- No `:` sigil on top-level entries: `use document`, not `use :document`. The sigil stays inside
  nested destructures: `use HTML: (:div)`.
- Destructuring after `use` is the ordinary operation: `use HTML` then `(:div) = HTML`.
  `use HTML: (:div)` stays as sugar for both.

## Semantics

`use` is managed at the file level, like a macro.

- **Static and hoisted.** Every `use` in a file, however deep, is collected into the file's
  manifest. All authority enters at load, and the host can see, bind and audit every request before
  the file runs. Writing `use` deep inside a block requests nothing at runtime.
- **Lexical binding.** Only the name is scoped to where `use` is written: that block and everything
  lexically inside it. The rest of the file can't see it.
- **Always the host.** `use document` always means the host's `document`. An enclosing scope that
  binds `document` itself doesn't intercept it, and the inner `use` shadows that binding. `use` is
  not a capture list. Capture from enclosing scopes is just closures.
- **One connection per entry.** Writing `use document` again in an inner scope gives you the same
  connection as the outer one, not a second one.
- **Placement doesn't affect `from`.** A call's `from` depends on where the call is made, not where
  the `use` it goes through is written. The plan is for every remote call to be tagged `from` its
  lexical calling scope (`from-names-calling-scope-2026-11-14.md`, not implemented yet). So where
  `use` sits only decides which code can see the name.

## Where it's allowed

In any lexical scope: the file, `actor { }`, class bodies, function bodies, and conditional and loop
bodies. In a conditional, the grant is hoisted, so the host binds the dependency whether or not the
branch runs. The name is still only visible inside that branch, so it can only be used there.

## What this retires

- **The `**` lineal header and `( DI ) actor { }`.** `use` covers both. With no header at all, a
  file is a singleton (`ast.fileKind` `'singleton'`).
- **"A file header must open the file".** That rule existed because an inline singleton had nobody
  to fill it in. With hoisting, the host fills in every `use`.
- **"A `*` header takes no DI".** A factory file's constructor body can contain `use`.
- **The trailing `*` section.** Replaced by `new =`. See "Factory files and the trailing `*`
  section" below.

## Factory files and the trailing `*` section

**Factory files stay.** A file that opens with a constructor form is a factory, as today:

- the lineal `*` header (`*` params `*`, then the body to the end of the file),
- `*{ … }`,
- `( params ) [->] *{ … }`.

Each one's constructor body may contain `use`. It's hoisted into the file manifest like any other
`use`, and visible to instance code. A call made by instance code comes `from` the instance.

**The trailing `*` section is retired.** A `*` section that follows singleton lines (members, then
a lone `*` as the file's `new`) is replaced by declaring `new`, the way any singleton does:

```brevity
use HTML

count *Integer = 0

new =
*
  seed Integer
*
count <- count + 1
```

The `new =` lineal form already exists (`class-singleton-forms-2026-11-13.md`). Its body is an
ordinary lineal body: it ends at the first blank line, unless a `--` stitch or braces hold it open.
A `*` section, by contrast, ran to the end of the file. `use` inside the `new` body is an
inner-scope `use`.

So a `*` at the head of a file makes a factory, and a `*` after singleton lines is an error that
points to `new =`.

## History

`use` existed before. In March it was renamed to `depends on`, then `uses` (`session-2026-03-15.md`,
`session-2026-03-20.md`), because `use` seemed "too quiet for a boundary crossing". Hoisting into
the manifest answers that worry: the boundary crossing is the manifest, which tooling can show in
one place, not the keyword where it's written.

## Open

- **Shadowing an enclosing local.** When an inner `use` shadows an outer local of the same name,
  it also changes where the authority comes from. Should that be silent, a warning, or an error?
- **`#` entries** (`"svc.bv": Svc #`, something to construct from) carry over unchanged. The open
  question in `file-singleton-header-2026-11-13.md` about whether `#` is a check or redundant still
  applies.
