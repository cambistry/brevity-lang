## Design discussion: actor types, composition, `ref`, and dependencies

### `ref` — the unifying keyword

`ref` bridges local and distributed:
- **Mutable local**: `ref x : Integer = 5` — mutable handle, mutate with `<-`
- **Child actor**: `ref counter = Counter(0)` — reference to a live child

Both are "an opaque handle to something stateful." Same concept at two scales. One word that bridges the local and the distributed — the whole CAM thesis in a keyword.

### Actor types: instantiation AND composition — no `behavior` needed

Initially considered a separate `behavior`/`trait` keyword for composable handler bundles, distinct from `actor`. But if an included thing can have `init`, private `$state`, handlers, and procs — it's an actor. The distinction collapses.

One concept (`actor`), two uses:
- `ref counter = Counter(0)` — instantiate as a child
- `include Library` — compose into myself

Rules for `include`:
- Union of handler interfaces (same-name handlers = overloaded clauses, matched in order)
- Shared proc space (can call each other's procs)
- State variables remain **private** to their defining `actor` block
- Each included actor's `init` runs as part of composite initialization

```
actor Library
  on go() ...
end#Library

actor Real
  init ...
  include Library
end#Real
```

This is mixins with encapsulated state. The `actor` block is already the right unit of encapsulation.

**Composition conflicts:**
- `on` handlers: no conflict, just overloaded clauses matched in order
- `as` blocks and `<-` (put) blocks: genuine conflict when multiple includes define them
- Resolution for `put`: the composing actor writes a new `<-` that integrates and super-calls each component's put. The composer understands the full shape and routes to each included actor's state. Same philosophy as the tree — the parent is the integrator.

### `is X` — do you need it?

Considered `is Mine` for "this file's actor is a Mine." But in the CAM tree, actors are always parented. The only cases for `is X` are root actor and tests — both are infrastructure, not everyday code. Normal flow:

1. Bare handlers = this file's own behavior
2. `actor X ... end#X` = define a child type
3. `ref x = X(...)` = parent instantiates child

No `is` needed.

### Dependency declarations: `depends on`

Renamed `use` to `depends on` for declaring external actor dependencies. `use` was too quiet for a boundary crossing. Considered: `external`, `extern`, `expect` (too laden with test connotations), `need`, `dependency` (noun, doesn't read as declaration).

`depends on` won because:
- Reads as English
- Two-word keyword has precedent (`repeat while`)
- Declarative, not imperative
- Parser: `depends` is a keyword, expect `on` next, consume both

Three forms following lineal/delimited duality:

```
depends on DB                          -- single
depends on User, Store, Logger         -- inline list
depends on /theme as Theme             -- path + alias

depends on                             -- lineal block
  DB
  Bluetooth as BT
  /services/auth as Auth
```

- Path references (`/some/path`) for addressing into the actor tree
- `as` for local aliasing
- NOT technically required for runtime (messages route through tree regardless)
- Provides **voluntary rigor** for compile-time type checking at boundaries
- Analogous to TypeScript's `any` escape hatch: omit `depends on` and messages still flow, but you lose static checking

### Ref lifecycle and garbage collection

- **Anonymous ref**: `User().hello()` — instantiate, call, discard. Nothing holds onto it, so it's garbage collected immediately after the expression.
- **Named ref**: `ref user = User()` — lives until it goes out of scope, then GC'd.
- **Exceptions**: refs survive scope if captured via `&` passing to a function that retains them, or if assigned to actor state (`$`).

Needs its own test file: `anonymous_ref.test.js`.

### `ref` instantiates from any source

`ref` works the same regardless of where the actor type comes from:

```
-- local type defined in same file
actor Counter
  init() ...
end#Counter
ref c = Counter(0)

-- aliased external dependency
depends on /my/child/actor as Child
ref a = Child(...)

-- direct path, no alias needed
ref a = /my/child/actor(...)
```

Universal meaning: "I now hold a reference to a live, stateful thing."

### `use` → `uses`?

Late thought: might be enough to just change `use` to `uses`. One character shifts it from imperative ("go use this") to declarative annotation ("this actor uses Remote"). Describes what the actor IS rather than giving it a command. Familiar, no collision, minimal change. Not fully decided but noted as a strong contender alongside `depends on` and `extern`.
