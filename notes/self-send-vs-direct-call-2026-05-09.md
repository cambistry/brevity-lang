# Self-send vs. direct call — when does the actor boundary actually exist?

**Date:** 2026-05-09
**Status:** design note. No implementation yet. Captures a working session walking from a current-state survey to a unifying principle.

## Current state across all three targets

Every Brevity-level function call on `self` (public `@`, protected bare, private `#`) is unconditionally compiled to a self-send through the actor's central dispatcher. There is no direct-call path and no inlining for ordinary calls. The only call-site fast path that exists today is for *constructor* calls of "pure value-tail wrapper" actors (`inlineExpandable` in JS) — and only in JavaScript.

Two name sets drive the call-site routing:

- `actorFnNames` — non-public functions: protected (bare) + private (`#name`)
- `publicFnNames` — public function names with `@` prefix (Erlang & Rust only; JS lacks this set)

### JavaScript (`src/codegen/javascript/`)

- **Definition:** all functions emitted as arms of `#dispatch(message)` (`classes.js:1007`). `receive()` (`classes.js:963`) routes to `#dispatch`. No direct method on the class for any user-defined function.
- **Call site:** `expressions.js:744` — `actorFnNames.has(name)` → `Structure.pack(await this.#selfSend(...))`. The `#selfSend` runtime helper (`classes.js:951`) constructs `{ id, op, from: '__self' }` and calls `#dispatch` directly, allocating a Promise and waiting on `#pending`. Silent functions take a fire-and-forget shortcut.
- **Public bare calls:** I could not find a branch handling a bare `@`-prefixed identifier; no `publicFnNames` set exists in the JS context.
- **Constructor calls:** `expressions.js:623` — `ActorName.create(binding, ...args)` directly. Exception: `inlineExpandable` actors (pure value-tail wrappers) get fully inlined as an IIFE at the call site (`expressions.js:631–657`). This is the only "compiler chooses something other than self-send" decision in the JS path.

### Erlang (`src/codegen/erlang/`)

- **Definition:** all functions become clauses of `handle_op(OpName, Message, Payload, Id, From)` (`program.js:381–448`).
- **Call site:** `expressions.js:198` — `actorFnNames.has(name)` → `genActorFnCallExpr` → `self_send(<name>, Args)` (`expressions.js:976/988/991/993`). `expressions.js:203` — `publicFnNames.has('@' + name)` rewrites the AST callee to `@name` and routes through the same path.
- **Self-send runtime:** `self_send/2` is a gen_server-style round-trip — posts to `self()` and awaits a reply.
- **Constructor calls:** `ActorName:start_internal(...)` directly.

### Rust (`src/codegen/rust/`)

- **Definition:** all functions become arms of `handle_op(...)` on the actor struct (`program.js:608–677`, generated by `handlers.js:18`).
- **Call site:** `expressions.js:397` — `actorFnNames.has(name)` → `genRustFnCallExpr` → `self.self_send("name", &payload)` (`expressions.js:1363/1387/1395/1397`). `expressions.js:401` — `publicFnNames.has('@' + name)` rewrites and routes through the same path.
- **Self-send runtime:** `self.self_send(op, &payload) -> Value` — synchronous in Rust; routes to `self.handle_op(...)`.
- **Constructor calls:** `ActorName::create(binding, args)` directly.

## What self-send actually pays for

Self-send drops the sync/async distinction — everything is async. That's principled but expensive:

- **JS:** Promise allocation + `#pending` Map churn + opName parsing + payload unpacking per call.
- **Erlang:** real message round-trip through the BEAM scheduler.
- **Rust:** `Value` (JSON) packing/unpacking on both sides + `match` on opname.

The uniform-async invariant was a useful simplification during bring-up. It's not a semantic commitment. Direct calls don't violate any actor-model property; they remove a queue insertion that wasn't observable.

## The unifying principle

> Self-send is the cost of cross-runtime semantics. Whenever the compiler can prove the receiver is in the same runtime as the caller, the call is direct, regardless of visibility.

Visibility (`@`/bare/`#`) is a *who can name this* axis. It says nothing about how the call should be invoked. We've conflated the two by routing every public call through dispatch, but the only thing that demands dispatch is "the receiver might be in a different runtime."

## Three levels, one principle

The optimization manifests at three levels, but they are the same rule applied at different scales.

### Level 1: intra-actor calls

Calls where the receiver is `self`. Today: self-send. Should be: direct.

The honest eligibility predicate is "does the function observe the dispatch envelope?" — narrower than I first thought:

- **Function-typed escape** — name used as a string-keyed lambda label (passed to `over`, stored in a state cell, etc.). Dispatch arm must continue to exist; direct emission can coexist alongside.
- **Message metadata reads** — `from`/`id`/sender introspection. Direct call has nothing to give.
- **Subscription side effects** — `subscribe@field` / `set@field` arms record subscriptions inside `#dispatch`. Visibility-tied; doesn't belong on the direct path.
- **Silent vs. awaiting reply** — silent already means "no return value expected." Direct call honors that for free.

`Reply` (`->`) is *not* a gating factor. Early return and trailing return are the same thing — both lower to `return value` in a direct-call body and to `post {re: value, to: _replyTo}` in a dispatch arm. One body, parameterized return mechanism. The dispatch arm becomes a thin shim that unpacks args, calls the direct method, posts the result.

### Level 2: closure-captured outer state

```brevity
value *Text = "hello"
@changer = *{ @modify = (t Text) { value <- t } }
```

`@changer` is a real, public, escapeable actor. The capture of `value` is the only thing that crosses a boundary. It is bound at definition time, in the parent's runtime — definitionally co-local. The grant is the cross-boundary act; operations through the grant aren't crossing anything new.

So `value <- t` should compile to a direct call into the parent's setter, not a `#set` message round-trip. The compiler knows lexically that `value` came from outer-actor scope; today's `{host, cell}` handle representation already carries the host reference. Codegen for `<-` on a closure-captured cell becomes `host.#setCell(name, t)` instead of `host.#send([{...}, "#set"], cellName)`.

Same applies to functions captured from outer scope, and to reads (`@field`).

### Level 3: co-located handles passed in

```brevity
Holder = (initial Integer) *{
  value *Integer = initial
  @inc = { value = value + 1 }
}

@new = { Holder(0) }
@Controller = (holder *Holder) *{
  @up = { holder.inc }
}
```

`@Controller(holder)` from within the same runtime → handle is co-local → `holder.inc` is a method call, not a message. `@inc` being public is irrelevant; visibility is naming, not invocation.

### Sources of co-location

- Lexical closure capture (always co-local — capture happens in the parent's runtime)
- Handle received as a constructor arg from a co-located caller
- Handle returned from a constructor *you* invoked
- Handle held in your own state, transitively co-located by the above

### Sources of possibly-remote

- Handle received as a message arg from a possibly-remote sender
- Handle deserialized from storage / network
- Anything where the call site couldn't prove co-location

## Compiler mechanism

A provenance marker on every actor reference. Two states is enough:

- **co-located** — referent lives in the same runtime as `self`. Direct calls allowed.
- **possibly-remote** — must use dispatch.

For constructors that accept handle parameters (like Controller), the body can't statically know its caller's runtime. Two implementation options:

1. **Monomorphization** — specialize Controller per call site. More code, but no runtime check.
2. **Runtime co-location bit on the handle** — every actor reference carries a flag; call sites check it.

```
isLocal ? ref.method(args) : send(ref, op, args)
```

The runtime-bit version is much simpler and the branch is predictable. In JS this is essentially free — the JS object reference is itself the local handle, and a `null`/instance check is the discriminant. In Erlang/Rust the flag bit is real but still cheap relative to the message round-trip avoided.

## Target asymmetry

- **JS:** every actor lives on the same event loop. Co-location predicate is *always true* unless an explicit boundary has been crossed (web worker). Aggressive lowering wins big.
- **Erlang:** parent and child instances are separate gen_server processes. Direct calls into another process's state aren't possible. Closure capture in Erlang is a captured pid + cell name; the optimization is mostly unavailable unless you change the runtime model for nested actors.
- **Rust:** depends on what an actor instance is. Independent task → Erlang's situation. Willing to wrap captured cells in `Arc<RwLock<...>>` → direct calls with synchronization, different cost trade.

## What stays expensive (and should)

- Cross-worker / cross-node calls
- Subscription delivery (subscribers might be remote)
- Function-typed value calls where the target is a string label resolved at runtime
- Message-metadata reads (`from`, `id`)

These keep using dispatch. No eligibility analysis required; they're already the right shape for it.

## Implicit yield: not a reason to keep self-send

Self-send creates a yield point with target-dependent strength:

- **Erlang:** strongest. Send goes through the BEAM scheduler; receiver runs on a separate process.
- **JS:** weakest. `#selfSend` resolves on the same microtask queue without yielding to macro-task work; `setTimeout(0)` yields, microtask `await` doesn't. `__tick__` is the real yield.
- **Rust:** depends on the runtime.

Where yield matters — long computation chains, draining other queued work — the right tool is explicit yield (`__tick__`), not implicit yield via accidental dispatch overhead. Leaving self-send in place as a backdoor for "occasional yield" is an implementation-detail leak: code becomes silently dependent on dispatch for responsiveness, and behavior shifts the day someone optimizes the call.

**Stack depth on deep recursion** is a related concern — direct calls compose stack frames; self-send via queue trampolines. Mostly a Rust concern (JS unfolds async stacks; Erlang is fine with deep recursion). Solvable case-by-case (TCO where supported, explicit trampoline where not, opt back into self-send for known-deep recursive helpers). Not a reason to keep self-send as the default.

## Forward references and backfill

Today's name-based dispatch sidesteps forward references for free — `#priv()` is just the string `"#priv"` until runtime, and the dispatch table is populated whole.

For direct calls, all three targets give forward references for free at the *language* level:

- JS class methods are order-independent within the class declaration
- Erlang functions are order-independent within a module
- Rust methods are order-independent within an `impl` block

The compiler needs a two-pass shape over each actor:

1. **Collect pass** — gather every function declaration with mangled name, params, signature, eligibility flags from provenance/escape analysis.
2. **Codegen pass** — emit bodies. Calls resolve against the table from pass 1.

**Cycle detection is not needed for direct-call lowering.** `f` calling `g` calling `f` is just recursion; targets handle it natively. Cycle detection only becomes relevant if/when bodies are *inlined* (substituted into call sites), where mutual recursion would expand forever. Inlining is a later, narrower optimization for short bodies; keep it as a separate phase.

- Direct-call lowering: backfill collect → codegen. **No cycle detection.**
- Inlining: backfill collect → cycle detect → inline acyclic, fall back to direct call on cycles. **Cycle detection only here.**

## Queues at boundaries, direct calls within them

Self-send today is doing two jobs in one:

1. **Cross-runtime communication** — genuinely needs a queue (ordering, cross-thread safety, cross-network anything).
2. **Intra-runtime function calls** — pure overhead.

Separating these gives a uniform policy across targets: **queues at runtime boundaries, direct calls within them.** What differs target-to-target is only *where the boundaries are*:

- **JS:** worker boundaries, host boundaries
- **WASM:** host boundary
- **Rust:** thread/task boundaries, process boundaries
- **Erlang:** process boundaries (cheap and ubiquitous on BEAM, so there are *more* of them than on other targets — but the rule is the same)

This reframes "actors are units of concurrency" as "actors are units of state and visibility; runtime boundaries are units of concurrency." The two concepts aren't bound together by the language — they're bound together when and only when the user puts an actor on the far side of a runtime boundary.

### Per-target wins from the separation

- **WASM:** the target where the difference is starkest. WASM has no free async runtime — every "async" you want has to live in linear memory or be bolted on through the host. Today's "every call is a queue insertion + Promise-equivalent" forces a hand-rolled event loop in WASM with all its plumbing imported/exported across the JS boundary. With direct-call-within-a-runtime, a Brevity program compiled to WASM becomes:
  - a linear-memory blob with one struct per actor instance
  - a function table of methods that call each other directly
  - a small inbox/outbox at the host boundary — the only place async exists

  The queue stops being the nervous system and becomes a thin shim at the genuine boundary. Much smaller target to compile to, and it composes naturally with how WASM hosts already think about FFI.

- **Rust:** sync `&mut self` methods, no `Value`/JSON round-trip on every call. Tokio (or crossbeam, or whatever) only shows up at thread/process boundaries. The bulk of a Rust-target program becomes idiomatic Rust again.

- **JS:** sheds Promise + `#pending` Map churn on the in-runtime traffic. Self-send remains for genuine cross-worker / network / host boundaries.

- **Erlang:** the interesting case. BEAM is the one platform where self-send is the *natural* shape — cheap processes, free supervision, scheduler integration. The Erlang strategy stays: each actor instance is a BEAM process, child actors are spawned processes, cross-process comms use gen_server-style messaging. What changes: *intra-process* function calls (currently lowered as self-send inside a single gen_server) become direct Erlang function calls. Keep all BEAM goodness for boundaries that genuinely cross processes; stop paying for it inside one process.

### A WASM-specific bonus

WASM also gives something the JS target can't: a real opportunity to reclaim the sync/async distinction at the language level for code that doesn't cross any boundaries at all. A pure-compute Brevity program (no DOM, no network, no IO) compiled to WASM is just a program — no event loop, no queue, no async coloring anywhere. That's a strong story for "Brevity for embedded things" or "Brevity for compute kernels you call from JS" that's basically unavailable today.

Worth treating as a first-class story when WASM lands: a no-IO Brevity program is a clean WASM module with sync exports, period.

## Suggested ordering

The wins compound, and the analyses build on each other. Order them by impact-per-effort:

1. **Closure-captured cell writes/reads in JS first.** Smallest, most concrete win. Eligibility is a syntactic property (lexical capture). No dispatch generation changes — just call-site lowering for captured handles. Cell writes are everywhere, so the impact is broad.
2. **Intra-actor direct calls** (private + protected, JS). Adds the analysis pass for "observes dispatch envelope?" and the body extraction. Dispatch arm becomes a shim.
3. **Co-location bit on handles** + direct calls through co-local handles to public methods. Generalizes (1) and adds runtime cost (cheap flag check). Probably collapses much of the public-call traffic to direct.
4. **Erlang and Rust** follow with the appropriate target adaptations. JS is the path of least resistance because of the single-event-loop model; the others come with their own concurrency-model questions.

Each step pays for itself without the next; each step makes the next smaller.
